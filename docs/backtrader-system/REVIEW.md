# 双策略入口方案复审

设计版本 1.2；2026-10-09。评审对象：v1.1 的 NL2Strategy + 上传 Python 方案与六份交接文档。方法：跨文档契约核对、失败场景推演、本地 Backtrader 预加载及事件循环源码查阅。本轮没有实现交易代码、没有运行交易测试或连接账户。

## 结论

建议保留 **Vibe 主应用 + Backtrader 统一运行 + 两种策略入口**。方案可以进入 P0 可行性验证与契约冻结；当前不能宣称已具备 paper/live 部署条件。

v1.1 在加入 Python 后有七处重要设计缺口，已修入 v1.2。修订的是设计要求；是否真正落实由 P0 与后续测试证明。双入口的最终目标仍包括回测和获授权的 paper；某入口暂时只能回测时必须报告部分完成。

## 发现与修正

| 编号/优先级 | 原方案问题与具体影响 | v1.2 修正及验收 |
|---|---|---|
| R1 / P1 | Python 可 `buy(size=10)`，后文却统一按目标比例算数量。实现 agent 可能重新算成 20 股，回测和 paper 接口各算一次 | 冻结 target_fraction / explicit_quantity 两种互斥模式；显式数量只能接受或拒绝，不能悄悄重算。T38 |
| R2 / P1 | 已将 SDK 拆入可信服务，但账本仍写“owner worker”，架构图也让沙箱代理写账；策略 IPC 与可更新授权的管理 IPC 未划开 | execution_service 独占账本、授权、SDK 和权威风控；strategy_worker 仅有策略通道；身份由启动绑定，不信任 actor/user 字段。T40 |
| R3 / P1 | 日线逐根执行不代表看不到未来。Backtrader 默认允许 preload/runonce，完整 DataFrame 也可能暴露给上传代码 | 认证运行关闭预加载/批处理，数据服务逐事件释放，完整历史文件不进入沙箱；测试正向索引、数组、文件、伪造 cursor。T39 |
| R4 / P1 | 补历史只能恢复部分指标；Python 的连续计数、上次成交等自定义状态可能重启归零，导致不同交易 | JSON 状态版本与 snapshot/restore；按原始输入/当时账户及成交事件影子重放，恢复指标与自定义状态并验证续跑。T41 |
| R5 / P1 | 回调先提交订单、稍后保存状态；若中途崩溃，会出现订单已经发出而策略还停留在上一次状态 | BrokerBase 代理暂存回调输出；正常完成后，可信服务原子保存 event_result/checkpoint/意图/预留。未知外部发送仍走原有对账，不盲重发。T42 |
| R6 / P1 | 用户代码死循环时 BT 循环停止；如果撤单、告警也依赖同一线程，停止机制一同失效 | 可信服务独立看心跳/事件超时，冻结新风险并按授权撤单，继续接成交与对账；策略通道不能阻塞管理通道。T43 |

定位：CONTRACTS 2 节（策略来源/数量模式/状态）、3 节（数据与数量）、5 节（账户所有权/事务/恢复）、6 节（两类通道与超时）、8 节（报告复核）；ARCHITECTURE 同步修正拓扑与职责；DELIVERY_PLAN 新增 T38–T44。

P1 表示进入自动交易实现前必须明确的设计问题；P2 表示会影响验收结论可信度的问题。它们不是已发现的已部署产品漏洞，系统尚未实现。

## 接手 agent 先做的五项实验

1. **目标部署平台隔离**：上传代码无法接触写 Gateway、凭据、账本、管理通道；限制 CPU、内存和执行时长。macOS/Linux 环境分别验证，不能用一套未验证的“子进程沙箱”覆盖所有平台。
2. **真实 BT 跨进程 Broker**：模拟官方 SDK 事件，证明 BrokerBase 代理能正确返回 native Order 通知，空 bar 时仍可处理取消/成交。账户事实在可信服务，策略状态在隔离运行时。
3. **事件与订单提交**：在 callback、checkpoint、intent 和派单边界逐点模拟 crash；确认未提交的新命令不派发、已提交重放不重复、券商结果未知会暂停对账。
4. **自定义状态恢复**：用含计数器、订单通知状态及非简单有限窗口指标的示例，比对连续运行与重启续跑；只比较现金/持仓不算通过。
5. **历史输入与报告复核**：未来数据不能通过数组/文件/IPC 提前获得；独立真实 BackBroker 复算订单日志得到一致成交/权益，用户篡改统计应被发现。

这些实验用于尽早揭示工程成本。失败时修正实现路径和契约，并保留可继续的独立工作；没有账户配置时仍可先完成上述离线验证。不能先完成大批前端页面，再发现策略运行与隔离无法成立。

## 首期产品范围的准确说法

- NL2：从自然语言生成系统当前支持的规则与 Backtrader 模板，用户确认规则卡；未支持的语义明确提示，不静默删减。
- Python：用户基于提供的 Backtrader 模板自定义指标、完整日线下的买卖条件及整股数量；遵循状态钩子、固定依赖、指定数据与订单入口。不是上传任意项目就能部署。
- 共同链路：固定版本 → 真实 BT 回测及检查 → 明确账户/额度授权 → IBKR paper → 订单/成交/持仓/停止/恢复。实盘启用仍单独授权。
- 两种来源各自记录 backtest/recovery/paper 结果；不以模板策略成功替代上传代码的验证，也不以 mock 替代券商模拟账户回报。

## 尚待实测的条件

上述五项工程实验；官方 SDK/Gateway 兼容；paper 身份及行情权限；可复现数据与公司行动来源；用户具体预算/风险/有效期。当前既未证明它们失败，也未证明它们通过。

此版维持单仓库、模块化实现。Python 增加的是隔离运行、有限通信、状态恢复与结果复核成本，无需因此引入多租户、分布式集群或消息中间件。先完整跑通一个 SMA 模板和一个有状态 Python 示例，再扩展策略种类。
