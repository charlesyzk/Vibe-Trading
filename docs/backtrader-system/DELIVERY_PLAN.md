# 分阶段开发与验收任务书

设计版本 1.2。适用仓库：`/Users/yaozekun/strategy_verification/vibe-trading`。本文件定义未来执行工作，不代表当前已实现或已测试。双入口复审见 REVIEW.md。

## 1. 交付目标与执行规则

首个完整交付是：自然语言生成规则或上传 Python 模板策略 → 冻结版本 → 真实 Backtrader 回测 → 用户授权 → 真实 IBKR paper 自动运行 → 订单/成交/持仓落账与推送 → 风险停止和重启后对账。两种来源单独记录回测/恢复/paper 通过状态；Python 仅能回测属于阶段性完成，不能把整个双入口目标标成完成。

**必须先完成的基础：** 代码/环境基线、统一契约、模板策略与用户上传策略的离线回测、账本/风险/环境隔离。之后才接有写权限的 paper 账户。

**随后完成：** AI/页面整合、真实 paper 全链路、故障恢复演练、可运维部署。live 接口可使用同一架构实现，但默认禁用，启用须另有真实账户授权和准入记录。

**本期范围外：** QMT/crypto 适配实现、复杂衍生品、多租户、多策略资金共享、任意依赖/任意系统权限的 Python 自动交易、为新功能直接重写 Backtrader 核心。允许用户按固定模板上传 Python，但可交易部署必须通过 OS 隔离和统一风控门槛。

每阶段更新 `PROGRESS.md`（执行 agent 新建），包括状态、修改文件、真实命令及退出码、证据路径、未完成项。阻塞记入 `BLOCKERS.md`：原因、证据、已试方案、需要的最小外部动作、可继续的独立工作。不得把环境阻塞转成伪通过。

## 3. P1：真实 Backtrader 离线闭环

### 实现

- 策略版本库与受控 SMA 编译器；用户上传的 `.py` 和参数声明可进入隔离回测执行器，不允许安装自带依赖。
- 明确 target_fraction / explicit_quantity 两种数量模式，定义 JSON 状态钩子与事件 checkpoint；上传代码无未来数据访问；同一订单日志可经独立真实 BackBroker 重放核对统计。
- 冻结数据 Feed、manifest、暖机、日历/时区/缺口/公司行动检测。
- 真实 Cerebro + BackBroker 执行，固定决策与数量语义；成本/滑点模型明确。
- 原生订单、成交、权益与未平仓持仓导出，带 execution provenance。
- `execution_backend` 路由与新 runner 协议；不能被原 SignalEngine 文件校验误挡，也不能绕过全部新校验。
- 资源超时/异常终止、输入输出路径约束。失败不会产生 success run_card。

### 验收

一份可手算的合成样本：精确指出哪根 bar 交叉、何时产生订单、下一 bar 什么价格撮合、买几股、费用多少、剩多少现金；最后留一笔未平仓以验其报告。再补真实冻结样本（有数据许可和完整 manifest）。合成与真实分开标记。

两次运行固定 bundle + 数据产生相同 decisions/orders/fills/权益（排除运行时间、随机 ID 等非业务字段）；改变未来 bar 不影响过去决策。若只 mock 了 Cerebro/BackBroker，P1 不通过。

## 4. P2：非代码用户完整回测体验

### 实现

- 新策略生成提示/工具输出受控 StrategySpec；不支持的自然语言条件在确认卡显示缺项，不静默省略。
- 提供 Python 模板下载、上传、参数表、源代码差异、检查结果和 backtest/paper 分开的能力状态；不将任意脚本误识别为策略文件。
- 规则卡展示精确标的、交叉/初始入场行为、资金数量规则、执行时点和费用。
- 确认后冻结版本；变更参数生成新版本；历史版本报告仍可追溯。
- 回测异步状态、原报告适配、后端标签、数据范围和限制。
- 新 execution API、前端组件和必要导航；原 native 研究功能无意外变化。

### 验收

用户从 UI 输入 SMA 意图到打开真实 BT 报告，无需手改 Python；另一个用户可上传符合模板接口的 Python 策略，经隔离校验后打开同格式 BT 报告。API 返回 source_kind、engine/backend 与 UI 一致。缺字段、违规依赖/代码、数据失败、进程崩溃能显示准确错误。前端 build 和相关测试通过，原回测入口相关回归通过。

UI 可先用 schema fixture 开发，但演示验收必须接真实本地后端产物；截图不构成引擎验证。

## 5. P3：IBKR Broker、账本与 paper 写入闭环

### P3a：先完成离线状态与风控

- `BrokerBase` adapter + 官方 SDK store，共享连接、合约解析、ID 管理、callback 队列。
- SQLite 迁移、订单意图、发送尝试、预留、回报/费用、outbox、快照、账户独占。
- 用户授权和两次风险检查、环境/账户校验、命令幂等、未知状态冻结。
- native Order/Position/notify_order 与实际回报映射；空数据时处理控制循环。
- worker 监督、受限 IPC、鉴权和研究隔离。Python 策略 worker 不持有 SDK/凭据；Broker service 仅暴露经授权的 Backtrader 订单通道。paper 与 live 走同一安全管线。
- 支持 Market/DAY 策略交易；为撤单验证可单独批准受支持的 Limit 测试订单，不能让日线策略偷偷改为 Limit。

门槛：所有负向用例中 placeOrder 调用数正确，错误条件下为 0；发生发送不确定性时不盲重试；未完成订单和预留准确保存。账本/SDK/权威风控只归可信 execution_service；管理通道与策略通道的越权用例通过，策略超时不影响服务接收成交及执行授权撤单。

### P3b：明确授权后的真实 paper 验收

用户确认具体 paper 环境、账户、标的、预算、有效期与风控后，才执行写入。不得用现有 IBKR_SETUP 的 live 4001 作为 paper 默认值。不能自动改变 Gateway 的 Read-Only 开关。用户 Python 要部署 paper，必须先通过独立进程无网络/无凭据、资源限制、Broker IPC 范围校验的负向安全用例；隔离未成立时，NL2 模板继续验收，Python 暂时只回测。

测试前读取账户和合约并核对身份；运行固定版本，经真实 adapter 向 paper 发送受限订单，记录 broker ack、execution、commission（若晚到保留 pending）、实际 position；测试取消本系统的可取消委托。订单在 paper 也有实际账户状态副作用，记录测试产生的持仓及收尾处理授权。

验收证据：脱敏账户/环境、bundle/hash、日志、映射 ID、事件序列、对账结果、UI 展示。真实回报不是 what-if；在线数据接 BackBroker 不是 paper。拒单同样是合法测试结果，但不能替代至少一次实际 paper 成交闭环。

如果当天无策略信号，可使用专门登记、明确标成 integration-test 的受控测试模板/手动测试意图验证 adapter，但不得声称生产 SMA 已经触发；生产 SMA 的决策链由离线/回放和随后实际信号分别验收。

## 6. P4：运行完整性、恢复、推送与运维

### 实现与演练

- 恢复对账、历史暖机抑制订单、决策游标、外部订单/仓位检测。
- 网络断开、Gateway 重启/重新登录、SDK 重连、worker crash、Web crash、主机睡眠恢复。
- 重复、乱序、迟到、缺失回报；成交发生在 cancel 请求后；费用/执行更正。
- 用户暂停、撤单、停止、恢复、明确授权的清仓；按动作显示“请求中/已确认/待对账”。
- 持久事件 SSE 补传、订单/实际持仓/目标仓位/风险 UI；健康度与数据时效。
- 安装、配置、运行/停止、日志、备份/恢复、版本回滚操作手册；秘密脱敏。

### 通过门槛

离线故障注入矩阵通过；paper 至少覆盖一次连接中断后的对账恢复，以及一次 worker 重启后的不重复下单。不能为了制造断线测试而操作 live Gateway。模拟出部分成交/特殊回报可证明状态机，若 paper 环境未自然复现需在证据上标明，不能伪装真实触发。

建议首期 paper 连续观察至少 5 个实际交易会话，覆盖日界线和至少一次有计划重启；这是工程观察最低建议，不代表策略盈利或实盘就绪。若期间无策略触发，应补充有明确授权的 adapter 验证和事件回放。所有关键阻断均有 UI 状态或持久告警。

| C：产品与 API | execution service/routes、AI 规则流程、frontend execution | schema 与事件样例；A/B 服务接口 | UI→真实后端集成、构建与交互用例 |
| 集成负责人 | pyproject/lock、共享 schema、路由注册、导航、部署手册、最终验收 | 全部工作包 | 完成矩阵、差异和上线边界 |

`pyproject.toml`、lockfile、API 总注册、公共 schemas、前端导航同一时刻一个负责人修改。变更契约先通知消费者，不能各自定义一个类似但不兼容的 Order/Signal。前端可以先用明确 fixture 并行，最终必须切真实服务。

建议里程碑演示：M1 手算样本真实 BT → M2 用户自然语言到报告 → M3 真 paper 下单回报闭环 → M4 重启/断线/停止演练通过。完成日期在 P0 后根据 SDK/数据/隔离结果估计；当前不能承诺“接个接口几天就生产可用”。

## 10. 运行命令与交付格式

已有 frontend `package.json` 包含 `test:run` 和 `build`，后端 pytest 配置位于 pyproject；当前 venv 没 pytest。执行 agent 安装已锁定的开发依赖后，应记录实际可用命令。新增 CLI 名称在实现前都只是设计，不得在验收文档声称已经跑过。

后续预期命令示例（**本轮未执行；目录/依赖建好后再用**）：

```sh
.venv/bin/python -m pytest agent/tests/execution agent/tests/bt_runtime
```

前端用仓库实际包管理器运行 `test:run` 和 `build`；先查 lockfile/README，不新增第二套依赖锁。paper 测试必须独立标记且默认排除于普通 CI，不能因开发机恰好运行 Gateway 而自动连接或下单。

每次交接至少提供：

1. commit/文件差异与基线；用户原修改是否触碰。
2. 完成阶段及验收矩阵，完整命令/退出码/输出证据。
3. 已知限制、阻塞与下一步精确动作。
4. 当前账户环境、是否连过账户/发过 paper 订单、是否遗留持仓/委托（没有则明确没有）。
5. 启停与恢复说明，默认 live disabled。

只有离线测试通过时交付名为“离线闭环完成”；真实 paper 未完成则标明阻塞。不能把“代码已写”扩大为“系统可自动实盘”。
